# repo-inbox — входящие и исходящие кросс-репные запросы

Issue с лейблом `inbox` — **запрос**, адресованный этому репо, и **не пункт плана**.
Он становится пунктом, когда владелец репо заводит в `TODO.md` пункт с указанным
`slug:`. Принятие нигде не хранится — оно выводится.

## Операция 1 — проверить входящие

```bash
REPO="$(git remote get-url origin | sed -E 's#.*[:/]([^/]+/[^/]+?)(\.git)?$#\1#')"
gh issue list -R "$REPO" --label inbox --state open \
  --json number,title,body --jq '.[] | "\(.number)\t\(.title)\t\(.body)"'
```

Для каждого issue:

1. Прочитать `slug:` из тела (это строка целиком, не упоминание в прозе).
2. `grep -n "<slug>" TODO.md` — искать **только по строкам-чекбоксам** (`- [ ]` / `- [x]`).
3. Слаг найден → запрос **принят**, работа идёт. Не найден → **не принят**, нужно решение владельца.

Показать пользователю две группы отдельно; непринятые — первыми. Не принимать
решение за владельца: это его репо и его план.

## Операция 2 — завести запрос соседу

Нужна работа в соседнем репо — **не редактируй его файлы**. Заведи issue:

```bash
gh issue create -R andrei-shtanakov/<target-repo> --label inbox \
  --title "<человеческий заголовок>" \
  --body "$(cat <<'EOF'
slug: <предлагаемый-слаг>
from: <этот-репо>#<слаг-своего-пункта>

<что нужно и по какому наблюдаемому признаку считать сделанным>
EOF
)"
```

- `slug:` — **запрос имени**, а не право его назначить. Владелец цели может принять
  под другим именем.
- `from:` — репо-отправитель; `#slug` опционален (у сообщения об ошибке может не
  быть пункта-источника).
- Лейбл ровно один — `inbox`. Состояние жизненного цикла лейблами не кодируется.

Если ждёшь результат — добавь себе в `TODO.md` тег `@blocked_by:<target>#<slug>`.

## Принятие, переименование, отказ (для владельца целевого репо)

- **Принять:** завести пункт в своём `TODO.md` с этим `slug:`.
- **Принять под другим именем:** завести пункт со своим слагом **и поправить `slug:`
  в теле issue**. Без этого вывод принятия сломается навсегда — тело issue
  единственная связь запроса с графом планов.
- **Отказать:** `gh issue close <n> --reason "not planned"` (не лейбл `wontfix` —
  допустимые значения `completed | not planned`).

## Границы

- Заведение issue у соседа **не нарушает** границ полирепо: правило запрещает
  редактировать *файлы* соседа, а issue файлов не трогает.
- Чужой `TODO.md` не редактировать никогда — принятие делает владелец.
- Кросс-репный обзор по всему флоту — не здесь, а `make inbox` в `devtools`.
