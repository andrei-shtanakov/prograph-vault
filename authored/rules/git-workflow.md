# Git workflow

Действует для репозиториев **со своим remote**. Согласовано с полирепо-механикой
(`authored/notes/2026-05-25-polyrepo-workflow-setup.md`: не submodules, гетерогенные
ветки, `--ff-only`).

Здесь — **как** едет изменение. **Когда и какого размера** — отдельное правило
`commit-pr-issue-granularity.md` (что заслуживает коммита, что PR, а что остаётся
пунктом `TODO.md`). **Как готовятся спека и план до PR** (локальная полировка,
один PR на пару) — `spec-authoring.md`. Кому принадлежит право на запись — ADR-ECO-007 (`write_scope`).

## Основной цикл
1. **Никаких прямых коммитов в дефолтную ветку** (`master`/`main`). Каждое изменение — на
   ветке `<kind>/<slug>`. `<kind>` — короткая пометка вида работы, **не закрытый
   список и не машинно-читаемое поле**: несущая часть имени — слug. Ходовые в этом
   репо (замер по 60 PR, 2026-08-15): `docs` 18, `notes` 8, `roadmap` 7, `adr` 5,
   `governance` 4, `rules` 2; `feat`/`fix` по 2, `chore` — ни разу. Прежняя
   формулировка перечисляла `feat/fix/docs/chore` как канон — она описывала кодовый
   репо, а не базу знаний, и была проигнорирована девятнадцатью разными префиксами.
   Единственное, чего стоит избегать, — дрейф форм: уже есть `note`/`notes`,
   `roadmap`/`roadmaps`, `contract`/`contracts`. Берите существующую форму, а не
   заводите её вариант.
2. Push ветки → открыть PR (`gh pr create`). В описании: что, зачем, какие контракты затронуты.
   Локальный мерж ветки в дефолтную в обход PR — та же ошибка, что прямой коммит.
3. **Ревью на PR — настраиваемо, по конфигурации репо:**

   **Copilot-ревью по умолчанию НЕ запрашивается** (решение владельца 2026-08-25:
   Copilot code review тарифицируется premium-запросами и за август 2026 сжёг 90%
   metered-бюджета аккаунта — ~10 PR/день по флоту плюс платные перезапросы; на
   репо с codex-review-гейтом Copilot к тому же лишь третий ревьюер после гейта и
   человека). Включение — строкой `Copilot-ревью: запрашивать` в секции
   «Git workflow» CLAUDE.md конкретного репо или явной просьбой владельца в
   сессии. Пока выключено — не запрашивать вовсе и **не перезапрашивать на
   «Copilot encountered an error»**: у кромки бюджета это троттлинг, и каждый
   перезапрос тоже платный (замер 2026-08-24/25: семь ошибок подряд на трёх PR).

   **Когда включено**, механика прежняя:
   - ревью не всегда запрашивается само — если его нет на PR, запросить явно:
     `gh api -X POST repos/<owner>/<repo>/pulls/<n>/requested_reviewers -f 'reviewers[]=copilot-pull-request-reviewer[bot]'`
     (замер 2026-08-16/17: `gh pr edit --add-reviewer` молча не срабатывает, а снапшот
     `reviewRequests` первые ~2 минуты пуст и выглядит как отказ — подождать и перечитать);
   - забрать замечания (`gh pr view <n> --comments`, при необходимости `gh api
     repos/<owner>/<repo>/pulls/<n>/comments`);
   - каждое **проанализировать**: валидное → фикс-коммит в ту же ветку; невалидное/
     неприменимое → ответить с обоснованием, **не применять вслепую**;
   - итерировать, пока не останется открытых actionable-замечаний (или все закрыты с
     обоснованием).

   **Ревью по умолчанию — терминальный прогон от ai-prosto** (решение владельца
   2026-08-28 по итогам дневной приёмки: в одном репо 10 CI-прогонов codex-review
   не отработали, вся содержательная работа шла вокруг ревью ai-prosto;
   терминальный канал ходит по подписке — дешевле и надёжнее):
   1. итерировать **локально**: `sh scripts/review/local.sh` до чистого вердикта
      (подписочный codex CLI — секунды на прогон, ноль долларов API);
   2. пушить **драфтом** — CI-итерации бесплатны (гейт отвечает deferred-вердиктом,
      Codex не вызывается);
   3. приёмочное ревью — `sh devtools/review-pr.sh <repo> <pr> --dry-run`, затем
      без `--dry-run`: вердикт публикуется как PR review от **ai-prosto**
      (approve / request-changes); находки отрабатываются как обычно;
   4. снятие драфта запускает CI-прогон гейта — он остаётся **advisory-фолбэком**:
      его красноту/зависание НЕ перегонять и не вахтить (класс отказов известен —
      нестабильность API); вердикт несёт ревью ai-prosto. Известное ограничение
      терминального ревьюера: он читает рабочее дерево чекаута, и на PR с новыми
      файлами может флапнуть ложное «файлов нет» — опровергать с evidence
      (`git cat-file -e <head>:<путь>`), не применять вслепую.
4. **Кто мержит — по типу сессии** (ADR-ECO-008):
   - **интерактивная сессия** (человек сформулировал задачу и присутствует в контуре) —
     **не мержить**: PR передаётся человеку. Это касается и агента, работающего в такой
     сессии, независимо от того, насколько он уверен в изменении.
   - **автоматический прогон** (maestro, spec-runner, cron, CI-driven агент) — **мержит
     агент**, если прогон не объявил `merge_authority: human` до старта. Объявление
     персистируется вместе с прогоном и по ходу не меняется.

   Тип определяется тем, **как сессия запущена**, а не тем, смотрит ли кто-то на неё
   сейчас: наблюдающий человек не делает автоматический прогон интерактивным.

   Мержит агент **только** когда шаг 3 закрыт — **включённые для репо** ревью собраны
   и каждая находка отработана (на репо с гейтом это зелёный или отработанный `report`;
   Copilot — только если он включён конфигурацией). Включённое ревью не пришло вовсе —
   это `unknown`: PR остаётся человеку, мерж не выполняется. Выключенное конфигурацией
   Copilot-ревью `unknown` НЕ является.

   **Всегда человеку, независимо от объявления:** PR, затрагивающий authority-root пути
   (ADR-ECO-004 I2), и PR, где базовый слой не смог предъявить evidence (fail-closed).

   **Автоматический прогон публикует сводку** в описании PR — три-четыре предложения
   (потолок шесть): что изменилось по существу, чего это стоило (что отвергнуто,
   упрощено, отложено), что осталось незакрытым. Сводка заменяет чтение дифа, поэтому
   рекламной быть не может: третий пункт пустой только когда он правда пуст.
5. **После мержа (человеком или агентом):** `git switch <default> && git pull --ff-only`; удалить
   влитую ветку в **обеих половинах** — локально и на origin: `git branch -d <branch>`
   (после **squash-мержа** `-d` откажется как «not fully merged» и `--merged` ветку не
   покажет — сверить, что `git diff <default> <branch>` пуст, и удалить `-D`; предикат
   «remote-ветка ancestor дефолтной» для удаления небезопасен — проверять локальный tip);
   `git push origin --delete <branch>`, если GitHub не удалил сам (замер 2026-08-17:
   auto-delete включён не во всех репо флота — 4 из 6 задействованных веток остались);
   затем `git fetch --prune`; убрать прочие влитые ветки.

## Ограничения
- Никогда не force-push в общие ветки.
- Не трогать другие репо (см. `repo-boundaries.md`).
- `pull` только `--ff-only` (кроме корневой папки набора — см. «Исключения»);
  грязные/detached/без-upstream ветки пропускать.

## Исключения
- **Репо без remote** (`spec-runner-tasks`): только локальные коммиты, PR некуда — цикл
  выше неприменим.
- **Корневая папка набора** (`all_ai_orchestrators`, remote
  `git@github.com:andrei-shtanakov/atp.git` — проверено 2026-07-26): remote **есть**, но это
  бэкап-зеркало cowork-бухгалтерии (ADR, статусы, черновики), не продукт — **PR нет**,
  коммиты идут прямо в `master`. Расхождение с origin (правки с разных машин)
  разрешается **merge-ом**: в локальном конфиге этого репо выставлен `pull.rebase=false`;
  глобальный дефолт не меняется, остальные репо остаются на `--ff-only`. Конфликты в
  living-доках (`COWORK_CONTEXT.md`) резолвятся **объединением фактов** обеих сторон, а
  не выбором стороны — обе правки обычно про разные события. Не путать с
  `ai-orchestrators-workspace`: тот — отдельный репо-зонтик (SSOT набора репо+пинов) и
  живёт по общему PR-циклу.
- **Внешний upstream** (`sdd-framework` на `git.epam.com`, владелец не ты): PR идёт
  владельцу апстрима, **self-merge невозможен** — следуй их ревью, шаг 4–5 адаптируется.
- **Папки без `.git`** — правило неприменимо.
