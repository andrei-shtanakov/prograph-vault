# Политика подписи узлов governance-бандла

**Решение владельца 2026-09-20:** подпись узла бандла создаёт мерж учётки
**`andrei-shtanakov`**. Формально — `AUTHORIZED_APPROVER_ACCOUNTS=andrei-shtanakov`.

Это то же значение, под которым подписаны обе предыдущие цепочки
(`verify-first-file-scope-group-targets-20260908` и
`mcp-launch-scope-spec-runner-485-20260914`): в их ледгерах записано
`policy: v1:31bf16586b6cfbb69a29b23d8850bfe57931d99b` — отпечаток списка из
одного этого элемента. Решение объявлено явно, а не выведено из прецедента.

## Зачем правило, если есть переменная

Механика §I12 (`devtools`, раскатана 2026-09-11 PR #191, дополнена devtools#221
и devtools#338) читает allowlist **из окружения в момент установления факта**,
и дефолт у неё пустой — «подписать не может никто». Нигде не хранить список —
сознательный fail-closed, и он правильный. Но у него есть цена, которую мы
заплатили 2026-09-20: сессия, выполнявшая механику **без** выставленной
переменной, засчитала человеческий мерж candidate-PR как неавторизованный и
перевела живую заявку в `invalidated`. Потеряно ничего не было, но узел
пришлось выносить заново.

С devtools#338 (`@id:approver-allowlist-process-boundary`, 2026-09-22) такой
исход в механике закрыт: пустая политика в процессе, устанавливающем факт, —
это отказ «политика недоступна» с **сохранением заявки**: факт не записан,
учётка не проверялась, повтор вызова с выставленной переменной завершает тот
же candidate. Основание: с devtools#278 candidate под пустой политикой не
создаётся вовсе, значит пустота на этой фазе — потеря значения между
процессами, а не решение о мержере. В `invalidated` по-прежнему ведёт только
установленный факт — мерж учёткой **не** из allowlist.

Правило закрывает то, чего механика закрыть не может: **значение объявлено
здесь**, а не живёт в памяти той оболочки, где его однажды выставили. Без
него отказ повторялся бы на каждом вызове из свежего окна.

## Как совершается акт

Одобрение узла — мерж candidate-PR **человеком**, и только он создаёт подпись.
Канонический способ, который называет механика:

```sh
AUTHORIZED_APPROVER_ACCOUNTS=andrei-shtanakov \
  make human-merge ARGS='<repo> <pr>'
```

**Но под branch protection он не проходит** (замер 2026-09-20, spec-runner):
`human-merge.sh` умеет только `--merge`/`--squash`, флага `--admin` в нём нет, а
защита требует approving review, которого на этих PR взять негде — автор PR и
единственная учётка с правом подписи это одно лицо, а форджа не даёт апрувить
свой PR. Фактически работает:

```sh
gh pr merge <pr> --merge --admin
```

Это обход, а не решение; расхождение заведено как devtools#277. Учётка при
этом обязана быть из allowlist — `--admin` меняет способ мержа, а не того, кто
мержит.

Переменная обязана быть выставлена у **того вызова механики**, который
устанавливает факт (фаза 3), а не только у мержа: без неё факт не
устанавливается. Цена ошибки с devtools#338 — повтор вызова, а не потеря
человеческого акта: финализация откажет с сохранением заявки, как описано
выше.

## Что агенту делать нельзя

**Агент не выставляет эту политику от себя** — ни «по прецеденту из ледгера»,
ни «очевидным значением». Механизм пишет отпечаток политики в журнал именно
затем, чтобы прошлое нельзя было переавторизовать задним числом новой
конфигурацией; выставив список самостоятельно, агент принимает решение об
авторизации вместо владельца и подделывает тот самый факт, который §I12 велит
устанавливать человеку.

Агент вправе **применять объявленную здесь политику**: подставлять её в вызовы
механики, которые устанавливают факт состоявшегося мержа. Изменение состава —
только явным решением владельца и правкой этого файла.

## Ловушка при чтении ледгера

`intent.fingerprint` волны одобрения и `policy_fingerprint` кодируются
**одинаково** — `v1:` + sha1 по отсортированному списку через запятую, — но
считаются по разным вещам: первый по составу DAG, второй по составу allowlist.
Прочитать один как другой легко, и 2026-09-20 это привело к ложному выводу
«политика уже решена, значение существует» на прогоне, где allowlist не
выставлялся никогда. Проверять принадлежность отпечатка следует пересчётом по
известному составу, а не по совпадению формы.

Записанную авторизацию видно в `run.json` прогона:
`ops.<approve-op>.authorization = {login, policy, source}` — там и только там
лежит факт «кто подписал и по какой политике».
