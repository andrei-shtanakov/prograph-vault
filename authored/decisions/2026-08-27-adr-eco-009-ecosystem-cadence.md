## TL;DR

1. **Scrum-ритуалы один-в-один не переносятся.** Они синхронизируют людей и ограничивают WIP исполнителей. Здесь исполнители — агенты (параллельны и дёшевы относительно), а дефицитный ресурс — **решения владельца**: human merge gates, эскалации, `budget authorize`, вердикты по findings. Ритуалы надо строить вокруг *очереди решений и латентности решений*, а не вокруг спринт-коммитмента.
2. **5 из 7 scrum-функций уже существуют де-факто** (дайджест/инбокс = standup, impresario = refinement, weekly status = review, governance/TDD-гейты = DoD, codex+Copilot+двухагентный гейт = code review). Строить их заново — чистая церемония.
3. **Реальных дефицита три:** (Д-1) security/supply-chain оси нет вообще; (Д-2) findings копятся без ритуала триажа — только за пилот F-01…F-39 + M-01…M-04; (Д-3) нет стандартной точки обязательства и выхода фазы, и нет очереди решений как артефакта.
4. **Д-3 (очередь решений) закрывается достройкой dispatcher, а не новым файлом** — панели `gate_waiting`/`needs_human` уже существуют; не хватает `waiting_since` (иначе decision latency нечем мерить) и источника «PR ждёт human merge». До этого Д-3 помечен как частично закрытый (v2). См. §6.1.
5. **Решение — Cadence v1:** 2 недельных автосенсора (Fleet Sweep — существующий; **Hardening Sweep — новый**) + 3 фазовых ритуала (Charter / Review / Retro), привязанных к ступеням пилота, а не к календарю. Плюс жёсткие анти-церемонные правила (П-1/П-2): ритуал обязан закрыть цикл записью — действием или явным «baseline подтверждён»; отчётный ритуал без действий 3 раза подряд приостанавливается, у сенсора же умирает не тишина, а **потребление** находок.
6. **«Оптимизация» в этом контуре — это стоимость и эффективность попыток, а не микрооптимизация кода.** $/задача, доля attempt'ов, убитых инфраструктурой, review-coverage — вот регрессии, которые бьют по продукту. В фазе M2/M3 review прошёл **1 задачу из 4** (`battle-log/2026-08-runs.md`, F-39) — и это заметили постфактум, а не сенсором.

## 1. Постановка

Запрос: «ритуалы вроде scrum, но не полная аналогия — например, еженедельный анализ кода на оптимизацию и безопасность, плюс аналоги sprint planning / review / retrospective».

Ответ ниже отвечает не на «как внедрить scrum», а на «какие обратные связи в этой экосистеме разомкнуты и каким минимальным ритмом их замкнуть».

## 2. Почему scrum не переносится один-в-один

| Что решает scrum | Есть ли эта проблема здесь | Вывод |
|---|---|---|
| Синхронизация нескольких людей | Нет: один владелец + флот агентов | Ритуал-как-встреча не нужен |
| Ограничение WIP исполнителей | Нет: узкое место не исполнение, а решения владельца (PR #7–#13 «ждёт human merge», 3 раунда эскалации на TASK-006, `authorize` #3/#4/#5/#8/#9) | Ограничивать надо **очередь решений**, а не задачи |
| Оценка и velocity | Story points бессмысленны, когда исполнитель — модель | Метрики: $/задача, interventions/run, escape rate |
| Демо стейкхолдерам | Стейкхолдер = владелец | Review нужен как приёмка exit-критериев, не как показ |
| Inspect & adapt | **Да, и это главное** | Переносим — это ядро ритуалов |
| Точка обязательства (что закрываем) | Частично: чартер kapelle §8 есть, стандарта нет | Переносим как Phase Charter |

**Тезис ADR:** каденс проектируется вокруг дефицитного ресурса. Здесь это внимание владельца. Значит каждый ритуал обязан либо *сократить* число решений, либо *подготовить* решение так, чтобы оно принималось за минуты, либо *убрать* решение из контура. Ритуал, который добавляет владельцу чтения без решений, — вредный.

## 4. Дефициты с evidence

**Д-1. Security-оси нет.** Проверено по 10 ядровым репо: ни CodeQL, ни gitleaks/detect-secrets, ни semgrep/bandit, ни `cargo audit`, ни `sobelow`/`mix_audit`. Единственные точки: `atp-platform/pyproject.toml:235` (`pip-audit>=2.10.0`) и `dependabot.yml` только у atp-platform. Конкретные векторы, специфичные именно для этого флота:

| Вектор | Evidence | Почему важно |
|---|---|---|
| Общий reusable-workflow: пин тегом, остаточный admin-хвост | `governance-gate.yml@governance-v2` вызывается из **22** репо; тег → `97c84db3`. **Сверка 2026-08-25:** tag-ruleset `governance-rule` активен (creation/update/deletion/non-FF заблокированы), но имеет bypass actors (RepositoryRole, DeployKey, текущий пользователь — always); обещанный шаблоном meta-enforcer **не существует** (planned batch 2) | Не «голый мутируемый ref», как считалось при ред. 1: ruleset предотвращает retag всем, кроме bypass/admin. Решение владельца 2026-08-25: **SHA-пин, двухэтапный rollout** (control-PR в зонтик с политикой и реальным чекером → 22 caller-PR на новый sha) — снимает остаточное доверие к ruleset/bypass/админ-контуру |
| Привилегированный путь мержа | `ai-orchestrators-workspace/.github/workflows/merge-broker.yml:70` — App-токен `contents: write` + `pull-requests: write` | Гигиена хорошая (`permissions: {}`, App-токен пинован по SHA `bcd2ba4`), но путь никем не аудируется по расписанию |
| Секреты и PII в evidence | `spec/.executor-logs/`, JSONL-трейсы, `battle-log/evidence/`, `_cowork_output/ops/install-merge-broker-credentials.sh`, `return_key.txt` | Агентные прогоны пишут много; утечка через коммит артефактов — реалистична |
| Бюджет как control | F-33: потолок $5.00 молча превышен до $5.92 на success-пути | Бюджет здесь — не UX, а контроль расхода/останова: его обход = класс security-дефекта |
| Prompt-injection поверхность | агенты читают README/issue/PR-комменты чужих репо; deployer ходит `DOCKER_HOST=ssh://` | Классический SAST этого не видит вообще |

**Д-2. Findings копятся без триажа.** F-01…F-39 (пилот) + M-01…M-04 (S2) + два файла findings по maestro/spec-runner. Часть чинится владельцем в течение суток — отлично; но нет точки, где спрашивают: что осталось открытым больше фазы, что стало системным, что мы решили принять. Системный вывод «advisory-review + бюджетные потолки систематически выключают review» был сформулирован лишь в итоге фазы, после трёх повторений.

**Д-3. Нет стандарта входа/выхода фазы и нет очереди решений.** Чартер существует в одном экземпляре (kapelle §8). Решения владельца рассыпаны по PR-тредам, эскалациям и `authorize`-командам; ни один артефакт не отвечает на вопрос «что сейчас ждёт меня и сколько оно уже ждёт».

**Д-4 (побочный). Дубль отчётности.** `2026-08-21-status.md` и `2026-08-17-linear-weekly-delta.md` пересекаются по git-активности и реестровому дрейфу; delta при этом шестой раз подряд начинается с «Linear не прочитан». Отчёт, который кормит сам себя, — кандидат на слияние.

## 5. Рассмотренные варианты

| # | Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|---|
| A | Полный scrum по календарю: недельные planning/review/retro | Привычно, предсказуемо | Три новых еженедельных документа поверх двух существующих; ритуал без команды вырождается в самоотчёт; риск, названный в ADR spec-governance-layer, — «ceremony is the risk» | ❌ |
| B | Только автосенсоры, без ритуалов рефлексии | Дёшево, ноль церемонии | Не закрывает Д-2 и Д-3 — а это как раз то, чего нет | ❌ |
| C | **Фазовые ритуалы + 2 недельных сенсора + правило анти-церемонии** | Ритм совпадает с реальной единицей работы (ступень пилота); сенсоры дают данные, рефлексия — решения; дешёвое внимание | Требует дисциплины «фаза объявлена/закрыта»; при затяжной фазе рефлексия отодвигается | ✅ **выбран** |
| D | Всё делегировать impresario/steward (governance-слой уже есть) | Ноль новых механизмов | impresario про продуктовые предложения и приоритизацию, не про операционный ритм и не про security; steward — про гейты. Натягивание даст неявную семантику | ⚠️ частично: **выходы** ритуалов идут в существующие механизмы (issues+inbox, ledger, dispatcher), но сами ритуалы живут отдельно |

Критерии оценки: покрытие Д-1…Д-4, стоимость внимания владельца, риск церемонии, переиспользование существующих механизмов.

## 6. Решение — Cadence v1

| # | Ритуал | Триггер | Исполнитель | Вход | Выход (обязателен) | Kill-criteria |
|---|---|---|---|---|---|---|
| R-1 | **Fleet Sweep** (существует) | пт, авто | агент | git флота, реестр | `status/YYYY-MM-DD-status.md` + строки в очередь решений | П-2 (отчётный): 3 отчёта подряд без действия |
| R-2 | **Hardening Sweep** (новый) | вт, авто | агент | манифест + overlay (S-0) | `hardening/YYYY-MM-DD-sweep.md` + **issue proposals** (создание — вне sweep) + строка в `hardening/ledger.md` | П-2 (сенсор): находки 3 цикла без реакции |
| R-3 | **Phase Charter** | старт фазы | сессия с владельцем | цель, задачи, риски | `cadence/phases/<фаза>-charter.md`: exit-критерии, бюджет run/task, что НЕ входит | — (без чартера фаза не стартует) |
| R-4 | **Phase Review** | exit-критерии достигнуты/фаза брошена | агент готовит, владелец принимает | чартер, git, battle-log | `<фаза>-review.md`: критерий → evidence → да/нет; факт стоимости vs план | — |
| R-5 | **Retro / Findings triage** | сразу за R-4 | сессия с владельцем | findings фазы, метрики | `<фаза>-retro.md`: каждый finding → fix now / issue / accept+документировать; **ровно одно** изменение процесса | 2 ретро подряд без изменения процесса → пересмотреть формат |

**Правила (это половина ценности ADR):**

- **П-1. Ритуал обязан произвести запись, закрывающую цикл.** Это либо действие (issue, решение, строка в ledger), либо **явное подтверждение отсутствия нового** («baseline подтверждён»). Второе — валидный результат, а не провал: для сенсора безопасности тишина есть успех. Молчаливый отчёт без обеих записей = ритуал не состоялся.
- **П-2. Kill-criteria разные для отчётных ритуалов и для сенсоров.**
  - Отчётный ритуал (R-1): 3 отчёта подряд, не породивших ни одного действия → приостановка решением.
  - Сенсор (R-2): *пустые прогоны — норма*. Умирает не сенсор, а потребление: критерий отключения — «находки заводятся, но 3 цикла подряд никто на них не реагирует» (issue не берутся в работу и не переводятся в accept). Иначе правило создаёт стимул находить шум ради выживания ритуала.
- **П-3. Одно изменение процесса за ретро.** Максимум два. Иначе процесс растёт быстрее, чем проверяется.
- **П-4. Не плодить механизмы.** Выходы идут в существующие каналы: GitHub issues + inbox (ADR-ECO-006), battle-log, dispatcher-вью, KB в prograph-vault. Новый — только `hardening/ledger.md`.
- **П-5. Ритуал не трогает репозитории.** Только чтение + issues/предложения. Human gate и правило «инструмент ≠ пациент» сохраняются.
- **П-6. Слияние отчётности.** R-1 поглощает раздел реестрового дрейфа из linear-weekly-delta; сама delta прекращается отдельным решением по судьбе Linear (вопрос открыт с 06-22).

**Что явно НЕ делаем:** не вводим спринт-коммитмент по календарю, не оцениваем задачи в поинтах, не заводим отдельный ритуал «standup» (дайджест уже есть), не строим governance-слой над пилотом (запрет из плана пилота).

## 6.1. Очередь решений (закрытие Д-3)

Д-3 — центральный по тезису ADR, и его нельзя закрыть упоминанием. Но и новый рукописный файл заводить нельзя (П-4): **механизм уже строится в dispatcher**.

| Что уже есть | Где | Покрывает |
|---|---|---|
| Панель `gate_waiting` — ожидающие гейты product-proposal | `dispatcher/docs/superpowers/plans/2026-08-12-pp-gate-waiting-panel.md` | решения по продуктовым гейтам impresario |
| `needs_human` + `loop_waits` над вендоренным `loop-state/v1` | `dispatcher/docs/superpowers/plans/2026-08-12-pp-needs-human.md` | ожидания цикла, требующие человека |
| Инбокс-счётчик кросс-репных запросов | github-checker TUI, ADR-ECO-006 | межпроектные запросы |

**Решение: очередь решений = агрегат dispatcher, а не новый артефакт.** Требуется достроить три вещи:

1. **`waiting_since` в контракте wait'а.** Сейчас идентичность wait'а — `(loop_id, iteration)`; времени начала ожидания нет, поэтому **decision latency (метрика №1 в §8) мерить нечем**. Поле нужно в `loop-state/v1` (владелец impresario) и в агрегате dispatcher. Это самый дешёвый и самый ценный шаг.
2. **Недостающий источник: PR, ожидающие human merge.** Крупнейшая по объёму категория ожиданий (kapelle PR #7–#13) сейчас не попадает ни в одну панель. Источник — GH API, владелец — dispatcher (или github-checker, если решить, что инбокс ближе).
3. **Строка очереди — контракт:** `решение · тип (gate | needs_human | pr-merge | escalation | budget-authorize) · ждёт с · возраст · блокирует (что стоит) · канал (где принять)`.

**Снапшот для тренда:** R-1 дописывает состояние очереди в конец weekly status (раздел «Очередь решений»), чтобы был исторический ряд. Живая истина — панель dispatcher и GH; файл — только след.

До того как п.1 и п.2 сделаны, Д-3 честно помечается как **частично закрыт (v2)**, и метрика decision latency в §8 считается вручную по GH-таймстампам на ретро.

## 6.2. Порог полного ритуала (масштабируемость каденса)

Фаз одновременно 4–6 (kapelle, disputatio, discovery, impresario-PP, dark-factory slice-0, codex-review-kit). Если каждая арка получает R-3/R-4/R-5, ритуальная нагрузка умножается на число арок, а расчёт стоимости внимания в §7 сделан для одной. Поэтому:

**Полный ритуал (R-3 + R-4 + R-5)** — если выполняется хотя бы одно:
- работа затрагивает ≥2 репозитория или меняет опубликованный контракт/гейт;
- ожидаемая стоимость прогонов > $10;
- изменение необратимо или трудно откатывается (миграция, релиз, право мержа);
- фаза является ступенью battle-testing пилота.

**Lite-форма (всё остальное):** три строки в `TODO.md`/плане репо-владельца — цель, exit-критерий, что не входит. Ни charter-файла, ни review, ни retro; находки идут в общий триаж ближайшего полного R-5.

**WIP-лимит — на ритуалы, а не на задачи:** одновременно не больше **трёх** фаз в полной форме. Это единственное место, где ограничение WIP из scrum осмысленно: оно ограничивает потребление внимания владельца, а не пропускную способность агентов. Четвёртая арка либо ждёт, либо идёт в lite.

## 7. Риски

| Риск | Митигация |
|---|---|
| Церемония: ритуалы съедают внимание, которое и есть узкое место | П-1, П-2; фазовая привязка вместо календарной |
| Шум сканеров (false positives) утопит сигнал | Baseline-файл в `hardening/`, в отчёт попадают **только новые** находки; известные исключения с датой пересмотра |
| Sweep сам становится вектором: агент читает недоверенный контент | Read-only, без исполнения кода репозиториев, сканеры — из пинованного тулбокса, сеть ограничена |
| **Инъекция через читаемый контент → мусорный или вводящий в заблуждение issue** | Выход sweep'а **advisory**: issue помечается `sweep/advisory` и не считается подтверждённой находкой до взгляда владельца; находка без `файл:строка` помечается «требует проверки» |
| Sweep живёт вечно и дублирует то, что должен делать CI | Метрика graduation (§8): доля проверок, переехавших в CI. Sweep обязан **сжиматься** |
| Стоимость sweep | Потолок в промпте + запись факта в ledger (тот же урок F-33) |
| Затяжная фаза — рефлексия отодвигается на месяцы | Правило: фаза длиннее 3 недель получает промежуточный R-5 по накопленным findings |

## 8. Метрики каденса

| Метрика | Источник | Зачем |
|---|---|---|
| Decision latency: медиана «PR готов → human merge» | git/GH | Прямой замер узкого места |
| Открытых решений в очереди на конец недели | R-1 | Растёт → каденс не справляется |
| Interventions / run | battle-log | Критерий перехода ступеней пилота |
| Review coverage (задач с состоявшимся review / всего) | battle-log | В M2/M3 было 1/4 — сенсор нужен |
| $ / задача, доля attempt'ов, убитых инфраструктурой | battle-log, `costs` | «Оптимизация» в реальном смысле |
| Escape rate: находки после мержа / все находки | Copilot+ревью vs post-merge | Качество гейтов |
| Возраст открытых findings (> 1 фазы) | battle-log, issues | Замыкает Д-2 |
| Security: новые advisories по severity, число мутируемых ref в путях исполнения | R-2 | Замыкает Д-1 |
| Registry drift: репо с активностью, но вне `COWORK_CONTEXT.md` | R-1 | impresario/discovery — по 2 недели |
| **Graduation в CI**: проверок R-2, перенесённых в CI репо / всего | R-2 ledger | Sweep должен вытеснять себя детерминированными гейтами |
| **Фаз в полной форме одновременно** | cadence/phases/ | Контроль ритуальной нагрузки, лимит 3 (§6.2) |
