# ADR-ECO-008a: merge broker — workflow GitHub Actions

**Статус:** Proposed (2026-08-19, Andrei) · **Решает:** Andrei (единственный владелец
экосистемы)
**Тип:** дополнение к
`authored/decisions/2026-08-19-adr-eco-008-merge-authority-by-session-type.md` (ADR-ECO-008)

**Скоуп:** где выполняется агентский мерж, где живёт приватный ключ merge-личности и кто
выпускает installation-токен. Закрывает открытый вопрос замера I4 «владелец выпуска
токена».
**Вне скоупа:** право мержа как таковое (ADR-ECO-008 D1), наблюдаемость (D6, ждёт
dispatcher), триггеры автоматических прогонов.

**Связано:** [[2026-07-18-adr-eco-004-governance-plane]] (I2 authority-root, I3 агентское
ревью — гейт, не апрув, I4 отзываемость),
`authored/notes/2026-08-19-i4-observability-measurement.md` (замер и выбор GitHub App),
`authored/rules/git-workflow.md` (операционный текст шага 4).

## Контекст

ADR-ECO-008 сказал, **кто** мержит, и оставил открытым, **где это исполняется**. Замер I4
поставил вопрос ребром: merge-личность выбрана (GitHub App, заведён как
`merge-broker[bot]`), но App аутентифицируется приватным ключом, и владелец ключа не был
определён.

Разница не техническая, а governance-ная. При локальном `.pem` рядом с оркестратором
отзыв авторитета означает «удалить файл на машине»: действие ненаблюдаемое, не
логируемое и никак не связанное с governance-слоем. I4 требует обратного — авторитет
отзываем только если за ним кто-то смотрит и может его снять.

## Решение

### D1 — Мерж исполняет workflow в целевом репозитории

Агентский мерж выполняет workflow GitHub Actions. Приватный ключ App хранится как secret
репозитория (или организации), installation-токен выпускается **внутри прогона**
(`uses: actions/create-github-app-token@v1` — форма `uses:` без `@ref` невалидна), живёт
минуты-часы и на диск не попадает.

Отзыв авторитета становится операцией governance-слоя: снять secret либо снести
установку App — оба действия видимы в интерфейсе GitHub и логируются, в отличие от
удаления файла на ноутбуке.

### D2 — Оркестратор инициирует, но не исполняет

Автоматический прогон вызывает workflow (`workflow_dispatch`), передавая номер PR.
Ключа он не видит, токена не получает, мерж не выполняет. Это разделение — не
церемония: оно означает, что компрометация машины с оркестратором не даёт права мержа,
а даёт возможность **попросить** о мерже — а просьба проходит через предусловия D3.

### D3 — Предусловия проверяются механически, до мержа, fail-closed

Workflow обязан проверить и отказаться при любом невыполненном условии:

1. **Ревью Copilot отработано** — операционализируется как «неразрешённых review threads
   нет» (GraphQL `reviewThreads { isResolved }`). Проверка «ревью запрошено» не
   годится и прямо запрещена: это разные утверждения, и подмена одного другим —
   способ, которым правило деградирует незаметно.
2. Прогон не объявлял `merge_authority: human` (ADR-ECO-008 D5).
3. PR не затрагивает authority-root пути (I2) — иначе мержит человек.
4. Базовый слой ADR-ECO-008 D2 предъявил evidence; неполные данные GitHub — отказ, а не
   продолжение.

**Обоснование первого пункта фактом.** В арке `discovery` ревью Copilot нашло два
реальных дефекта в PR #9 **после** того, как четыре автономных гейта и adversarial-критик
дали зелёный, и ещё один в PR #78. Это единственный слой, поймавший их, — поэтому его
проверка обязана быть содержательной, а не отметкой о запросе.

### D4 — Файл workflow есть authority-root

`.github/workflows/<merge-broker>.yml` определяет, кто и при каких условиях мержит.
По I2 такие артефакты агент-иммутабельны: **изменения самого workflow мержит человек**,
агентский путь на него не распространяется.

Без этого пункта конструкция замыкается порочно: агент, имеющий право мержа, правит
файл, которым это право выдано, и расширяет себе полномочия штатным путём.

### D5 — App не апрувит то, что мержит

Права `Pull requests: write` технически позволяют App поставить approve. По I3 агентское
ревью — гейт, а не апрув. Самоапрув перед самомержем схлопывает два независимых условия
в одно и запрещён.

## Последствия

**Права App — минимальные:** `Contents: RW`, `Pull requests: RW`, `Metadata: R`.
Установка — точечная, в конкретные репозитории, не «All repositories».

**Роль merge broker зафиксирована этим решением, а не именем App.** App называется
`merge-broker` по выбору владельца; совпадение с ролью удобно, но роль определяется здесь.

**Чего это решение не даёт.** Наблюдаемости. Мерж станет различимым в `mergedBy`
(`merge-broker[bot]`) и классифицируемым в steward, но dispatcher его по-прежнему не
показывает — блокер D6 остаётся, `todo://dispatcher/agent-merge-observability`.
Включение D1 после этого ADR по-прежнему невозможно.

**Во флоте прецедента нет:** ни App-токенов, ни мержащих workflow сейчас не существует
(замер 2026-08-19). Это будет первый, поэтому его стоит собрать в одном репозитории и
перенести в остальные копией, а не писать заново — по правилу единообразия callers.

## Открытые вопросы

- **OQ-1.** Точная механическая формулировка «ревью отработано». `isResolved` по всем
  threads — кандидат; неясно поведение, когда Copilot не оставил ни одного thread
  (нет находок против нет ревью). Кандидат: отсутствие ревью — `unknown`, то есть отказ.
- **OQ-2.** Один workflow на репозиторий или один центральный на весь флот. Копия в
  каждом репо проще по правам и хуже по дрейфу; центральный требует cross-repo прав,
  то есть более широкой установки App.
- **OQ-3.** Нужен ли интервал между сигналом готовности и мержем (наследуется из
  ADR-ECO-008 OQ-2 и здесь не решается).
- **OQ-4.** Строгость пина action'а, выпускающего токен. Флот пинит тегом
  (`actions/checkout@v4`, `astral-sh/setup-uv@v5`, изредка точной версией
  `@v8.1.0`), и `@v1` этой конвенции соответствует. Но подвижный мажорный тег у
  шага, **выпускающего merge-токен**, — поверхность цепочки поставок иного веса, чем
  у `checkout`: компрометация апстрима даёт не сборку, а право мержа. Кандидат —
  точная версия или SHA именно для этого шага; решение не принимается здесь, потому
  что оно меняет практику пиннинга всего флота, а не одного файла.
