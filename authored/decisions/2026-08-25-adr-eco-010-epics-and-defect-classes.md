# ADR-ECO-010: Эпики и классы дефектов

**Статус:** **Proposed** (на ревью) · **Дата:** 2026-08-25 · **Решает:** Andrei
(единственный владелец экосистемы)

**Скоуп:** как артефакт работы (пункт `TODO.md`, коммит, PR, issue) относится к потоку
задач; грамматика и носители тега; где живёт реестр потоков; кто и что из него считает.
**Вне скоупа:** гранулярность коммитов/PR (см. `authored/rules/commit-pr-issue-granularity.md`);
governance-плоскость и вычисляемый статус roadmap-элементов (ADR-ECO-005 D1 — здесь ничего
не меняется); зеркалирование эпика в метки GitHub (возможное расширение, §Ограничения).

**Связано:** [[2026-07-27-adr-eco-005-plan-fields-two-plane-model]] (операционная плоскость
и её теги), [[2026-08-07-adr-eco-005a-typed-operational-owner]] (типизованный владелец —
тот же приём: значение типизуется, грамматика становится контрактом),
[[2026-07-28-adr-eco-006-cross-repo-issue-inbox]] (кросс-репный запрос = inbox-issue),
`authored/contracts/epics/v1/` (контракт этого решения),
`authored/contracts/plan-fields/v2/` (плоскость `TODO.md`),
умбрелла `workspace-manifest.toml` (прецедент живочитаемого флотового факта).

---

## Корневая причина (тезис первым)

В полирепо у работы есть **четыре плоскости артефактов** — пункт `TODO.md`, коммит, PR,
issue — и **ни одной общей оси**, которая говорила бы, к какому потоку артефакт относится.
Каждая плоскость типизована по-своему: `plan-fields` дал пунктам `@id`/`@owner`/`@blocked_by`,
governance-плоскость дала roadmap-элементам вычисляемый статус, github-checker дал снапшот
открытых PR и issues. Все три отвечают на вопрос «что это за артефакт» и ни одна — на вопрос
«частью чего он является».

Следствие наблюдаемо и измеримо. Замер 2026-08-25: **291 открытый пункт** `- [ ]` в 21
`TODO.md` (≈248 уникальных — maestro присутствует дважды из-за worktree). На GitHub-стороне
тем же замером — **2 открытых issue и 1 открытый PR на 20 репо**: бэклог по правилу
`commit-pr-issue-granularity.md` живёт в `TODO.md`, а issue — исключение. Значит GitHub-корпус
эпика это не открытый снимок, а **поток**: PR открываются и мержатся десятками в неделю
(дайджест 07-27→08-03 насчитал ~200 коммитов по флоту), и именно эта история сегодня
безымянна. Работа над одним потоком физически размазана по 4–6 репо: срез 0
Dark Factory жил в maestro, deployer, dispatcher и steward одновременно. Через час-другой
после переключения контекста принадлежность конкретного issue невосстановима без
археологии, а недельный дайджест robin, сгруппированный по репо, показывает такой поток
как несколько несвязанных абзацев.

Это не дефицит трекера. Linear как внешний трекер был испробован и отвалился: пять
недельных отчётов подряд (06-22 → 08-03) фиксируют «коннектор требует переавторизации,
ноль `LABS-NN` в коммитах», а роль трекера кросс-репных запросов явочным порядком заняли
GitHub-issues (ADR-ECO-006). Ось потока должна жить **там же, где живёт работа** — в
артефактах и в git, — а не во внешней системе, доступность которой не является свойством
экосистемы.

```
программа  (продукт/инициатива, kind: ecosystem | external)
    └── эпик  (поток задач, конечная арка либо standing)
            ├── пункт TODO.md      @epic: / @defect:      → плоскость состояния (dispatcher)
            ├── коммит             трейлер Epic: / Defect: → плоскость движения (robin)
            ├── PR                 трейлер в теле
            └── issue              трейлер в теле
```

---

## Решение

### D1 — Два уровня: программа → эпик; ровно один эпик на артефакт

*Программа* — продукт или инициатива (`eco` — сама экосистема, `airun` — сторонний
продукт). У программы есть `kind: ecosystem | external`: срез «развитие экосистемы vs
сторонняя работа» — это фильтр по одному полю, а не ручное перечисление эпиков.

*Эпик* — поток задач внутри программы. Идентификатор всегда двухуровневый, ровно одна
точка, глубже не вкладывается:

```
^[a-z0-9][a-z0-9-]{0,31}\.[a-z0-9][a-z0-9-]{0,63}$
```

Префикс программы **входит в идентичность эпика намеренно**: цель «опознать» требует, чтобы
сырая строка `@epic:airun.kapelle-m3` читалась без похода в справочник. Цена — перенос эпика
между программами не является переименованием и разрешается только через надгробие (D7).

Стоячий фон — эпик со статусом `standing` внутри своей программы (`eco.ops`, `airun.ops`),
а не отсутствие эпика. Так покрытие остаётся 100 %, а вопрос «докатили ли до конца»
задаётся только аркам.

**Ровно один эпик на артефакт, не список.** Артефакт в двух потоках ломает агрегат двойным
счётом; пограничная работа принадлежит более конкретному эпику. Два тега — диагностика
(D6), даже когда значения совпадают.

### D2 — Класс дефекта ортогонален эпику и не является его значением

`@defect:<class>` / трейлер `Defect:` — необязательный тег, ставится **только** на починки.
Он не заменяет эпик: баг, возникший внутри работы над эпиком, несёт оба тега.

Довод от противного: если класс дефекта — это значение поля эпика, то баг внутри работы над
`eco.dark-factory-slice0` получит эпик и **выпадет** из подсчёта «где чаще всего ломается».
В статистику попадут только баги вне эпиков, то есть ответ будет систематически занижен
ровно на период самой активной разработки — там, где багов больше всего. Ортогональность
даёт два честных среза вместо одного искажённого: по эпику и по классу, плюс бесплатный
третий — сколько дефектов породил каждый эпик.

Список классов закрыт и живёт в реестре (`[defect_classes]`); расширяется тем же PR-ритуалом.

### D3 — Носитель — git-трейлер и инлайн-тег, метки GitHub в v1 не используются

В `TODO.md` — инлайн-тег на **первой строке** пункта, рядом с существующими
(`plan_state._UNCHECKED` разбирает пункт построчно и продолжений не видит):

```
- [ ] Собрать консоль продюсера @id:df-console @epic:eco.dark-factory-slice0 @owner:github:andrei-shtanakov
- [ ] Починить падение резюма пайплайна @id:pipe-resume @epic:eco.ops @defect:pipeline
```

В коммитах, теле PR и теле issue — трейлер в завершающем trailer-блоке, в одной грамматике
с `Co-Authored-By`:

```
Epic: eco.dark-factory-slice0
Defect: pipeline
```

Почему не метки GitHub: метку надо завести в каждом из ~15 репо и заново при каждом новом
эпике (мутация, новый verb в github-checker), а PR открываются агентами через
`gh pr create --fill` — метка сама не проставится. Главное же: **robin читает git-зеркала, а
не GitHub API**, и трейлер в коммите позволяет считать активность по эпикам вообще без
доступа к GitHub — свойство, которое пять отчётов подряд оказывалось решающим. Ограничение
метода зафиксировано в §Ограничения.

### D4 — Область обязательности, наследование и исключения

Обязателен ровно один эпик у:

- каждого управляемого пункта `TODO.md`;
- каждого first-party PR и issue;
- каждого first-party non-merge коммита.

**Наследование.** Коммит, однозначно привязанный к PR, наследует эпик PR (при squash трейлер
и так уезжает в историю; при merge-commit — нет, поэтому наследование считается по привязке
PR↔SHA, а не по тексту сообщения). Собственный трейлер обязателен там, где наследовать не от
чего: прямые коммиты в `master` — то есть зонтичный репо, где PR нет по политике.

**Исключения** перечисляются явно в реестре и только там: merge-коммиты, коммиты ботов
(dependabot и прочие по логину), импортированные и завендоренные артефакты, а также вся
история до `adopted_at`. Без явного перечня «100 % покрытие» стало бы зависимым от способа
подсчёта, то есть недостижимым по построению.

### D5 — Грамматика и значения разъезжаются по разным домам

- **Грамматика** (id эпика, slug дефекта, трейлер, схема реестра, реестр диагностик) — это
  кросс-репный контракт без репо-владельца, значит KB: `authored/contracts/epics/v1/`.
  Потребители **вендорят пиненую копию внутрь**, как plan-fields.
- **Значения** (какие программы и эпики существуют, их статусы, пороги покрытия) — это
  флотовые данные, они меняются еженедельно и живут в умбрелле:
  `ai-orchestrators-workspace/epics.toml`, читаются инструментами **живьём по пути**.

Прецедент прямой: `workspace-manifest.toml` — тоже общефлотовый часто меняющийся факт,
и его читают по `--manifest`, а не вендорят. Вендоренный еженедельно меняющийся реестр
протух бы к моменту первого же чтения; вендоренная грамматика — не протухает.

Закрытый список значений — это и есть защита от опечатки: `eco.dark-factroy` не станет
молча новым эпиком, а даст `EP-UNKNOWN`.

**Связь пинов машинная.** Вендоренный `plan-fields` обязан фиксировать зависимость от
`epics/v1` — версию, source SHA и `tree_sha256` манифеста, — и conformance-сюита проверяет
эту связь. Иначе «делегирует грамматику» через полгода станет второй копией regex.

### D6 — Кратность и конфликт — диагностика, а не молчаливый выбор

- нет тега → `EP-MISSING`;
- эпик не в реестре → `EP-UNKNOWN`;
- два `@epic`/`Epic:` в одном артефакте → `EP-MULTIPLE`, **даже если значения совпадают**;
- связанные артефакты (пункт → коммит → PR → issue) несут разные эпики → `EP-CONFLICT`;
  ни одно значение не выбирается «по старшинству» молча;
- тело артефакта не получено или усечено → состояние `unavailable` и `EP-UNAVAILABLE`,
  но **не** `missing`.

`Defect` в проверке единственности эпика не участвует и образует отдельный ортогональный
срез.

### D7 — Надгробия

Перенос эпика между программами или переименование — только через надгробие в реестре:

- `moved_to` взаимоисключён с живым `status`;
- target обязан существовать;
- цепочки и циклы запрещены — перенос сразу указывает на конечный id;
- старый тег принимается **только** у исторических артефактов; новый открытый артефакт со
  старым тегом получает `EP-MOVED`;
- id программы нельзя удалять или переиспользовать, пока на него ссылаются эпики или история.

Правило то же, что у `@id` в plan-fields: идентичность не переиспользуется никогда.

### D8 — Два порога и поплоскостная эскалация

Порог переключения и порог принуждения — **разные точки**, обе в реестре
(`[coverage_policy]`):

- `robin_cutover_*` — TODO ≥ 0.98, issues ≥ 0.90, PR ≥ 0.90 — разрешает сменить главную ось
  дайджеста;
- `missing_error_after` — дата, начиная с которой `EP-MISSING` блокирует; порог принуждения =
  100 % минус явный grandfather-реестр.

Совпадение порогов остановило бы CI на оставшихся процентах, поэтому они разведены.

**Малый знаменатель — не процент.** Замер 2026-08-25 дал 2 открытых issue и 1 открытый PR на
весь флот: доля по такому знаменателю — шум, один неразмеченный артефакт обваливает её до
нуля. Поэтому `[coverage_policy]` несёт `min_sample`: плоскость с меньшим числом артефактов
сообщает `insufficient_sample`, а не долю, и не участвует в решении о cutover. Иначе решение
о смене оси дайджеста принимал бы один случайный PR.

**Структурные диагностики блокируют сразу**, не дожидаясь разметки: `EP-GRAMMAR`,
`EP-UNKNOWN`, `EP-MULTIPLE`, `EP-MOVED`, `EP-DEFECT-*`, `EP-CONFLICT`. Переходный период
устраняет старый долг — он не должен разрешать добавлять новый.

Эскалация задаётся по плоскостям: новый/изменённый пункт TODO — CI-error; новый PR —
required check по телу; issue, созданный через github-checker, — валидация на создании;
старые открытые PR и issues — grandfathered до правки или закрытия.

### D9 — dispatcher показывает состояние, robin — движение

Плоскости dispatcher: TODO, issues, PR. Плоскость robin: коммиты. Коммит-трейлеры отвечают
на «что двигалось за окно», а не «что открыто сейчас»; складывать их в один счётчик — значит
складывать поток с запасом.

**Связь commit→PR восстанавливается не эвристикой.** Номер `#123` в subject squash-коммита —
соглашение, а не доказательство; merge-коммит трейлера не содержит вовсе. Поэтому
`snapshot/v2` публикует **окно attribution по смерженным PR** (`number`, `merge_commit_sha`,
`commit_shas`, нормализованные `epic`/`defect`, `merged_at`, `completeness`, `window_days`,
`truncated`), а robin сопоставляет локальные SHA с этой проекцией. Dispatcher из того же
контракта потребляет только открытые issues/PR; attribution-окно — транспорт для robin, и
это записано в контракте явно.

Robin **не пересчитывает семантику** github-checker: он читает опубликованный машинный
результат, ровно как `freshness.py` читает вердикт steward'а («Robin never recomputes the
sensor's semantics»). Отсутствие или протухание артефакта даёт явную строку UNKNOWN, а не
ноль. Альтернатива — robin ходит в GitHub API сам — отвергнута: это второй коллектор и
вторая копия парсера трейлеров.

### D10 — `unclassified` — bucket классификации, не эпик

Неразмеченный артефакт не соответствует грамматике `<program>.<epic>`, не принадлежит
программе и не имеет `kind`. В API он маркируется отдельно
(`{"type": "classification_bucket", "id": "unclassified"}`), в `[epics]` не записывается и
**остаётся отдельной строкой при любом `?kind=`**: скрыть неразмеченное фильтром — значит
выдать частичный агрегат за полный.

Строка присутствует всегда, даже когда счётчик ноль: исчезающая строка читается как «всё
размечено» ровно тогда, когда данных нет.

**Полнота и происхождение показываются по каждой плоскости отдельно.** Общее `N open` без
указания, какие плоскости прочитаны, запрещено: при недоступном снапшоте эпик показывает
`TODO: 7 · issues: —(unavailable) · PR: —(unavailable)`, а не `7`.

### D11 — `last_activity_at` считается только по плоскостям с доказанной семантикой

Время наблюдения — не время активности. `generated_at` снапшота им не является.

- каждая плоскость отдаёт `last_observed_at`;
- `last_activity_at` вычисляется только из источников с доказанной семантикой
  (`updated_at` у issues/PR, дата коммита) и сопровождается `activity_sources`;
- плоскость `TODO` в v1 в `last_activity_at` **не входит**: `plan-fields` не даёт даты
  изменения пункта (`provenance.commit` — коммит наблюдения), а `git log -L`/blame на
  перенесённой строке врёт. `last_changed_at` — отдельный будущий deliverable.

Отсутствующее поле честнее поля с недоказуемой семантикой.

## Последствия

**Хорошо.** Одна обязательная метка на артефакт даёт три среза (программа, эпик, класс
дефекта) и фильтр ecosystem/external. Ось потока живёт в git и переживает недоступность
любой внешней системы. Опечатка ловится закрытым реестром, а не замечается через месяц по
кривому агрегату. Ретро-разметка воспроизводит уже отработанный ритуал `@id`-backfill PF-2B.

**Плохо.** Плюс один обязательный тег на каждый артефакт и дисциплина трейлеров у агентов.
Реестр требует ведения: незаведённый эпик блокирует работу (`EP-UNKNOWN` — error). Ретро-
разметка — это ~20 PR по репо. Перенос эпика между программами дорог by design (D1/D7).

**Риск и его страховка.** Главный риск — агрегат, который выглядит полным, будучи частичным.
Страховка встроена: `unclassified` всегда видим (D10), полнота показывается поплоскостно
(D10), `unavailable ≠ missing` (D6), cutover robin только по порогу (D8), а до него —
shadow-раздел рядом со старой осью.

| Ф0b | `ai-orchestrators-workspace` | human-reviewed сид `epics.toml` |
| Ф1a | `dispatcher` | парсер/валидатор в `packages/plan-fields`, вендоренные пины обоих контрактов |
| Ф1b | `ai-orchestrators-workspace` | CI-сенсор: `EP-MISSING` = warning, структурные — блокирующие |
| Ф2 | `github-checker` | `snapshot/v2`: нормализованные `epic`/`defect`, состояние полноты, attribution-окно |
| Ф3 | `dispatcher` | read-model, `/api/epics`, web-вкладка, MCP; явные `unclassified` и `unavailable` |
| Ф4 | все | ретро-разметка **только открытого**: TODO — через PR (≈248 пунктов, ~20 PR), открытые PR/issues — правкой тела (на 2026-08-25 это 3 артефакта), история не переписывается |
| Ф5 | `robin-runtime` | сначала shadow-сравнение, затем смена главной оси по достигнутому порогу |
| Ф6 | `ai-orchestrators-workspace` | эскалация: `EP-MISSING` → error по дате и порогу из реестра |

Порядок не произволен: Ф3 без Ф2 покажет заведомо неполный агрегат, который прочитают как
полный; Ф5 до Ф4 сделает неполные данные главной осью; Ф6 до Ф4 остановит CI на старом долге.

Кросс-репные запросы (в частности `snapshot/v2` к github-checker) идут inbox-issue по
ADR-ECO-006, а не правкой в чужом репо.

## Известные ограничения

1. **В вебе GitHub эпик находится только полнотекстовым поиском (`in:body`); кликабельного
   фильтра по метке нет.** Зеркалирование трейлера в метки — возможное расширение, отдельная
   задача; в v1 сознательно не делается.
2. Коммит наследует эпик от PR по привязке; при merge-commit в тексте истории трейлера не
   будет — атрибуция держится на attribution-окне снапшота, а не на тексте.
3. Ретро-разметка покрывает только открытое; закрытые пункты и старые PR остаются без эпика
   намеренно (закрытые пункты несут номера PR — восстановимо, если понадобится). Практическое
   следствие замера: срез «по эпику открыто N issues» ещё долго будет околонулевым по
   построению — ценность GitHub-плоскости здесь в потоке смерженных PR, не в открытом снимке.
4. Открытые PR и issues размечаются правкой тела; история не переписывается.
5. `last_activity_at` не включает плоскость TODO (D11) до появления доказуемого
   `last_changed_at`.

## Открытые вопросы

- **OQ-1.** Порог `robin_cutover_*` задан числами 0.98/0.90/0.90 априорно, а плоскости
  issues/PR при нынешнем объёме почти наверняка будут отдавать `insufficient_sample`. Первый
  замер после Ф4 покажет, по каким плоскостям решение о cutover вообще принимается; пересмотр
  порогов и `min_sample` — правкой реестра, не ADR.
- **OQ-2.** Покрытие коммитов измеряется, но не гейтится (наследование делает знаменатель
  спорным, а гейтить спорный знаменатель — значит гейтить методику подсчёта). Пересмотреть
  после двух полных недель shadow-режима robin.
- **OQ-3.** Нужен ли `[grandfather]`-реестр как файл или достаточно даты `adopted_at` плюс
  состояния «issue не редактировался с тех пор». Решается на Ф6 по фактическому объёму долга.
