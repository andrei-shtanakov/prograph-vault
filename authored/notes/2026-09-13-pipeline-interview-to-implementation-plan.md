# Пайплайн «интервью → реализация»: состояние и план развития

**Дата:** 2026-09-13
**Статус:** proposed — план предложен fleet-агентом (devtools) по итогам
замера состояния; принимает владелец. До принятия пункты в `TODO.md`
репо-владельцев не заводятся.

Порядок и границы наследуют решение владельца 2026-08-31 (спека
behaviour-конвейера devtools, §1): пайплайнов **два** — внутренний (развитие
экосистемы) и внешний (сторонний продукт); внутренний делается первым,
внешний переиспользует его как участок, добавляя сверху impresario и
discovery-интервью в customer-фрейме. Развилок под внешний вариант во
внутреннем не закладывать.

governance-долг (триаж devtools 2026-09-13, шесть workstream-пунктов).

## 2. Где живут артефакты (правило для всех этапов)

Всё, что является **утверждением о продукте**, живёт в git репо-владельца и
приходит туда PR-ом. Всё, что является **состоянием процесса**, живёт вне
git на машине оператора. Правило репо-границ: [[repo-boundaries]].

**В репо продукта** (репо-цель конвейера):

- discovery-brief — нулевой узел бандла, рядом с charter (этап 1 плана);
- бандл `workstreams/<ws-id>/spec/00-charter.md … 30-decomposition.md`;
- tasks-спека `spec/<ws-id>-tasks.md` со штампом approve; waivers и замеры
  `spec/.tdd-evidence/`;
- код, тесты, конфиги приложения — integration-PR-ами;
- `profiles/` конвейера и `.github/codex/review-context.txt` (authority-root,
  мерж человеком);
- evidence живых прогонов `docs/evidence/`;
- пиненая копия approved ProductProposal (этап 3 плана).

**Вне репо продукта:**

1. Портфельные объекты impresario (`impresario/pilot/`: идеи, бэклог,
   оценки, решения QG-4/QG-5, PP) — существуют до рождения репо продукта и
   сравнивают продукты между собой; продукт получает копию своего PP.
2. Состояние процесса: леджеры прогонов `devtools/out/governance-runs/`,
   журналы интервью `~/.discovery/sessions/`, state-DB и логи spec-runner
   под `spec/.executor-*`, `.steward/gate_verdicts.jsonl`.
3. Инструментарий: конвейер, ревью-обвязка, мерж-гвард остаются в devtools;
   продукт несёт только конфигурацию для них.

**Следствие: репо продукта рождается на границе QG-5.** До approve продукт
живёт только в impresario.

## 3. Этапы

Этапы последовательны по зависимостям. Единица планирования — workstream
через тот же конвейер; даты не ставятся.

### Этап 0. Стабилизация внутреннего участка

Назначено триажем devtools 2026-09-13 (`devtools/TODO.md`, раздел «Триаж
открытого governance-долга»); здесь только выходной критерий.

1. Fidelity ревью (devtools#136, #166).
2. Fail-honest supersede (devtools#177, #168, #181, #175).
3. Контракт файловой цели verify-first (devtools#201, inbox из spec-runner),
   следом остаточный долг task_bridge (#123, #162, #198, #200).
4. Остатки document-runner (devtools#204) до следующего behaviour-авторинга.
5. spec-runner: релиз ≥2.36 с verify_first; закрытие spec-runner#429 →
   переписанный #427.

**Выход:** один workstream проходит `spec-loop` → approve → `run --strict`
→ accept-pr → merge без ручных исключений и без новых issues класса
«обвязка».

### Этап 1. Вход конвейера из discovery-brief (engineer-фрейм)

Первый непройденный участок; одновременно триггер, ради которого discovery
получил runtime («вызываемость стадии прогоном»).

- **Контракт входа.** `spec-loop --brief <path>`: бриф обязан пройти
  вендоренный gate_check со статусом pass, иначе fail-closed. Хэш брифа
  входит в frontmatter charter как upstream — §I2-сверка анкера видит бриф
  как остальные узлы.
- **Авторинг S2 из брифа.** Промпты charter/requirements (`governance/ops.py`)
  получают бриф как источник: G-NN и FR-NN переносятся с трассировкой, не
  пересочиняются. Гвард: каждый Must-FR брифа встречается в requirements.
- **Провенанс.** Бриф лежит в бандле как нулевой узел, доставляется тем же
  PR, что и charter. Граница author ≠ execute discovery сохраняется: PR
  открывает конвейер.
- **Приёмка.** Живой прогон: интервью engineer-фрейма → бриф → spec-loop →
  approved tasks-спека → исполнение spec-runner; evidence в журнале.

Зависимость: этап 0, пункты 1–3 (та же поверхность task_bridge/S2).
Владелец изменений: devtools.

### Этап 2. Вызываемость стадии Need из прогона

- **Шаг S-need** перед S2: `discovery start --frame engineer --target <repo>`
  → цикл `status` → пауза `awaiting_input` → `answer` от человека →
  `brief --out`. Пауза — тот же паттерн, что `waiting_human_merge`: повтор
  одной команды продолжает прогон.
- **Публикация:** решить, публикуется ли транскрипт вместе с брифом или
  только бриф (журнал интервью сегодня живёт только в `~/.discovery`).
- **Предусловие — решение владельца: соло-режим.** Без реальных
  стейкхолдеров интервью вырождается в самоопрос (открытый вопрос
  `discovery/TODO.md`). Либо мини-форма фрейма для одного человека, либо
  правило «стадия Need только при наличии стейкхолдера, иначе вход из брифа
  этапа 1».
- Фаза 3 grounding discovery имеет собственный триггер и сюда не входит.
- **Приёмка.** Прогон, где ни один артефакт не создан руками: от
  `spec-loop --need` до integration-PR.

### Этап 3. Внешний вариант: impresario сверху конвейера

- **Шаг 0 — bootstrap репо продукта** на границе QG-5: `repos.sh bootstrap`,
  регистрация в `workspace-manifest.toml`, governance-gate caller, волна
  `profiles/` и review-context, пиненая копия PP. Сегодня делается руками.
- **Вход.** `spec-loop --proposal <PP-id>`: subject и ws-id выводятся из PP,
  идентификатор PP входит в frontmatter charter, интервью идёт в
  customer-фрейме, evidence QG-4/QG-5 ссылается из charter.
- **Открытые решения владельца** (до старта этапа): целевой репо первого
  внешнего продукта; **Mode-2 для продукта, охватывающего несколько репо**.
  Компиляция decomposition → maestro отклонена для внутреннего лейна; для
  кросс-репного продукта либо режем на воркстримы по репо с inbox-issues
  ([[2026-07-28-adr-eco-006-cross-repo-issue-inbox]]), либо возвращаем
  вопрос. Решается не сейчас: первый внешний продукт может быть
  однорепозиторным, и тогда вопрос не возникает.
- **Приёмка.** Одна идея из pilot-бэклога доведена до влитого
  integration-PR с непрерывной цепочкой evidence: Idea → PP → бриф → бандл →
  tasks → PR.

### Этап 4. Замыкание петли

- S8-вердикты и merged-факты integration-PR проецируются в статус PP
  (impresario) и в наблюдение dispatcher.
- Ритм по [[2026-08-27-adr-eco-009-ecosystem-cadence]]: fleet-check
  показывает workstream'ы на человеческой границе с `waiting_since`.
- Эксперимент libretto для ритуала ревью-стопа — опциональный пункт с
  числовым критерием, вне критического пути.

## 4. Развилки и решения владельца

| Решение | Нужно к | Рекомендация |
|---|---|---|
| Этап 1 параллельно этапу 0 или после | старт этапа 1 | После пунктов 1–3 этапа 0: обе работы правят task_bridge и S2 |
| Соло-режим интервью | старт этапа 2 | Правило «Need только со стейкхолдером», иначе вход из брифа |
| Транскрипт публикуется или только бриф | этап 2 | Только бриф; транскрипт — состояние процесса |
| Целевой репо первого внешнего продукта | шаг 0 этапа 3 | Новый репо через bootstrap |
| Mode-2 для кросс-репного продукта | этап 3, только если продукт многорепозиторный | Отложить до первого такого продукта |

- Пункты этапа 1 → `devtools/TODO.md` (владелец изменений — devtools).
- Bootstrap репо продукта (шаг 0 этапа 3) → кандидат в скрипт devtools
  после первого ручного прохода.
- Решения из §4 фиксируются в этой заметке правкой статуса на `accepted`.
