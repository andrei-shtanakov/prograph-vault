# Замер I4 и выбор merge-личности

Замер выполнен 2026-08-19 перед возможным включением ADR-ECO-008 D1 (мержит агент
в автоматических прогонах). Это **снимок на дату**, а не living-документ: когда факты
изменятся, его не правят, а заменяют новым замером, помечая этот `superseded`.

Вопрос замера ровно один: **выполняется ли инвариант I4 ADR-ECO-004** — «авторитет
отзываем только если кто-то *смотрит* на агентские мержи».

**Ответ: нет.** Причём не «чего-то не хватает», а «механизм устроен так, что агентский
мерж будет записан как человеческий».

## Факты

**1. Агент ходит на GitHub под личностью владельца.** `gh` авторизован как
`andrei-shtanakov`; проверено `gh api user` → `andrei-shtanakov`, exit 0. Токен
действителен: этой же личностью за сессию созданы PR и issue в четырёх репозиториях.

**2. Эта же строка стоит в `human_identities`** — `steward/profiles/approval-policy.yaml:6`:

```yaml
human_identities:
  - github:andrei-shtanakov
agent_identities:
  - github:dependabot[bot]
```

**3. Человек проверяется первым, и это сделано намеренно** —
`steward/src/steward/gatecheck/approval.py:76`, комментарий в докстроке: «listed human is
never reclassified by a misleading hint». Следствие: агент, выполнивший `gh pr merge`
сегодня, классифицируется **`human`**. Не `unknown`, не `agent`. Finding не возникает.
Молча.

**4. Личности для агентов флота не существует.** В `agent_identities` только Dependabot.
Без отдельного субъекта различить агентский мерж невозможно **ни одним** инструментом
ниже по течению — сколько его ни дорабатывай.

**5. Классификация `agent` сегодня жёстко запрещена** —
`steward/src/steward/gatecheck/approval.py:227`: любой актор, распознанный как агент,
получает `GC-APPROVAL-MISSING` с текстом «agent_merge is disabled by policy
(ADR-ECO-004)». Это константа, а не политика.

**6. dispatcher не знает понятия актора мержа.** Merge-команда и исход `merged` есть
(`dispatcher/dispatcher/core/actions.py:574`), актора и evidence — нет. Поверхности
наблюдения, которую требует I4, там не существует.

**7. Мержи внутри прогона вообще вне механизма.** В арке `discovery` maestro слил четыре
воркстрима в интеграционную ветку **локально** — без PR и без события на GitHub. Для
steward и dispatcher их не существует; наблюдаемой единицей остаётся только финальный PR.

## Вывод

ADR-ECO-008 D6 предписывает поведение для этого случая сам: нет наблюдаемости — прогон
обязан вести себя как `merge_authority: human`. Значит **D1 остаётся записанным и
невключённым**, и это не дефект решения, а сработавшая в нём оговорка.

Включение сегодня дало бы не отсутствие контроля, а **ложную запись о контроле**:
агентские мержи легли бы в статистику человеческими, а `GC-APPROVAL-MISSING` молчал бы.
Тот самый класс дефекта, ради которого писался governance-слой.

**Вторая причина не включать, независимая от техники:** ADR-ECO-008 имеет
`status: proposed`. Мерж документа в базу знаний не равен ратификации решения; до неё
D1 не является действующей политикой, даже когда I4 будет закрыт технически.

## Решение: целевая merge-личность — GitHub App

Выбор владельца, 2026-08-19. Не machine user.

- App даёт отдельного субъекта вида `…[bot]` — агентский мерж различим **на уровне
  GitHub**, а не по догадке инструмента, и естественно попадает в классификацию `agent`
  (в `classify_actor` хинт `"Bot"` уже распознаётся).
- Права и установка ограничиваются конкретными репозиториями; доступ отзывается узко,
  без касания личной учётки владельца.
- Machine user различимость тоже даёт, но остаётся обычным `User`: отдельный аккаунт,
  PAT, ручная ротация и явная allowlist-классификация. Приемлемо как временная мера,
  слабее отвечает требованию ADR-ECO-004 пункт 8 о **narrow, revocable** identity.

## Что из этого следует

**Handoff в steward:** разрешение `agent_merge` должно стать политикой, а не константой
(`approval.py:227`), и App-личность внести в закрытую классификацию. Без первого гейт
заблокирует то, что ADR-ECO-008 разрешил; без второго различать будет нечего.

**Handoff в dispatcher:** actor-aware evidence `agent_merge` / `human_merge` и
наблюдаемая поверхность для I4.

**Открытый вопрос — владелец выпуска installation token.** Вероятные кандидаты: runtime
оркестратора либо узкий merge broker. **Не** dispatcher UI: наблюдатель, который сам
держит ключ от наблюдаемого действия, перестаёт быть независимым наблюдателем.

**Порядок:** ратификация ADR-ECO-008 и закрытие I4 — независимые условия, и включать D1
можно только когда выполнены оба.
